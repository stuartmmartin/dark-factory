# ledger — service notes
- A reference service: it proves every scaffolding seam with a small double-entry domain. Copy its shape, not its domain.
- Business rules: `application/use_cases/*` (process) and `application/policies/*` (math). The `R<n>` lists are the contract.
- Double entry: `POST /v1/journal-entries` → `PostJournalEntry` (rules) + `policies/double_entry` (balance math, the "Journal entry" and "Transfer" acceptors); `GET /v1/accounts` → `ListAccounts`; `GET /v1/accounts/{id}/balance` → `GetAccountBalance`. Not built yet: entry events, account types (normal balances), a reversal endpoint, statements/pagination, multi-currency entries.
- `journal_entries`/`journal_lines` are append-only (trigger, and sb_app has only SELECT/INSERT): never add an update or delete path; corrections are reversing entries. Lines reference `(account_id, tenant_id)` with a composite FK because FK checks bypass RLS.
- Amounts are rejected, never rounded, when they exceed the currency's minor units. Format them for the wire with `domain.amounts.to_decimal_str` (trims `NUMERIC(38,18)` storage zeros without rounding).
- `ledger.client` (`uv run ledger-cli`) is an HTTP-only demo client: it must import nothing else from `ledger`, so it can become its own workspace member once a human registers one in the guardrail configs. Its config is `client/settings.py` (`LEDGER_CLI_*`): a second settings module, a deliberate C5 exception until the client is its own member.
- The seams: HTTP `POST /v1/accounts` → `OpenAccount` → account + audit + outbox `AccountOpened` → relay → Kafka → inbox consumer → `RecordAccountOpened` (per-tenant count); Temporal `AccountCountSnapshot` → activity → `SnapshotAccountCount`.
- Local: `make up infra`, then `make up ledger`; API at http://localhost:8001/docs and admin at http://localhost:8001/admin. Dev auth needs the `X-Tenant-Id` header.
- `make seed SVC=ledger` opens "Operating cash" (USD) for the demo tenant `00000000-0000-0000-0000-0000000000d3` through `OpenAccount` (idempotency key `seed-account-1`, so a re-run replays). If host port 8001 is taken, set `SB_LEDGER_API_PORT` (like the other `SB_*_PORT` variables).
- The dev image holds only third-party deps; compose bind-mounts `src`, `migrations` and `libs/py`, and `compose/dev-entrypoint.sh` installs them editable at start, so no edit needs a rebuild (run `make build ledger` after a `uv.lock` change). The API reloads itself (`--reload`). The worker and consumer run as in prod, with no reloader, so a crash exits and compose's `restart: unless-stopped` restarts them; pick up an edit in them with `make restart ledger` (`make up ledger` does not recreate unchanged containers).
- Only `ledger-migrate` gets `LEDGER_MIGRATOR_URL` (BYPASSRLS) and `LEDGER_ADMIN_DATABASE_URL`; they are optional in `Settings`, and `ledger.migrate` refuses to run without them. The API, worker, consumer and seed get only the `sb_app` URL. compose requires `SB_AUTH_MODE`, the `SB_*_PASSWORD`s and `SB_ADMIN_*` (`${VAR:?}`).
- Only the API mounts the admin, so only `ledger-api` gets `LEDGER_ADMIN_*` (compose, and `ledger-admin-secrets` in the dev k8s overlay). They are optional in `Settings`; `build_api` calls `settings.admin_credentials()` outside prod before building anything, so a missing or short credential fails the API at startup. The worker, consumer, migrate and seed never receive them (`make seed` blanks them, since it runs inside the API container).
- `LEDGER_ENVIRONMENT` and `LEDGER_AUTH_MODE` are required. Dev auth and the admin exist only in `local/dev/test/ci`.
- The prod overlay uses `auth_mode=oidc`, which is not implemented yet (`backend_for` raises `NotImplementedError`): the prod `ledger-api` Deployment crash-loops (and `deploy.yml`'s rollout step fails) until OIDC lands. That is intended (fail closed). Do not stub it, and never set dev auth in prod.
- Kubernetes: `deploy/k8s/ledger/{base,overlays/dev,overlays/prod}`. `make k8s-render SVC=ledger ENV=dev` and `make k8s-validate`. The Deployments get `ledger-config` and the `ledger-secrets` Secret (`LEDGER_DATABASE_URL`); in dev only `ledger-api` also gets `ledger-admin-secrets` (`LEDGER_ADMIN_*`); only the `ledger-migrate` Job also gets `ledger-migrate-secrets` (`LEDGER_MIGRATOR_URL`, `LEDGER_ADMIN_DATABASE_URL`). Secrets are never stored in the repo. `images.yml` builds and pushes only from `main`; `deploy.yml` runs only from `main`, deploys only a SHA on `origin/main`, by digest, and runs the migrate Job to completion before it applies the Deployments. Namespaces (with the Pod Security `restricted` labels) are created by a cluster admin from `deploy/k8s/cluster-admin/`; the deploy credential is namespace-scoped. Before deploying, `deploy.yml` verifies the image's build provenance (`gh attestation verify`: built by `images.yml`, from `refs/heads/main`, at that SHA), so a re-pointed tag is refused. Human setup: BOTH GitHub Environments `dev` and `prod` restrict deployment branches to `main`, and `prod` also requires reviewers; `KUBECONFIG_B64` is defined only as a per-Environment secret, never at repository or organisation level; its credential is bound to a namespace-scoped Role that covers ConfigMaps, Services, Deployments, Jobs and NetworkPolicies (plus pods and pods/log reads) and cannot create Namespaces. The prod egress CIDRs are TEST-NET placeholders until a human sets them.
- The admin's list views run as `sb_app` with no tenant set, so RLS shows them **zero rows**. That is expected (Plan 4 ruling D9). Never point the admin at `migrator_url`.
- Idempotency: a sequential replay returns the stored account (200 instead of 201; the body carries no replay flag); the same key with a different body is 422 `idempotency_key_reused`; a racing duplicate is 409.
- `python -m ledger.consumer` runs the outbox relay loop and the inbox consumer in one `TaskGroup`. A handler error or a fatal `PublishFailed` exits the process non-zero on purpose: the supervisor restarts it. Never catch and loop.
- Failure mode: a **permanent** handler error (a message that can never succeed, e.g. it fails validation or a bug) crash-loops the consumer: the message is never committed, so every restart redelivers it, fails again, and blocks its partition (every later message on it waits). That is platform policy (`on_poison=None`: no dead-letter topic yet), chosen so no event is silently dropped. Diagnose from the logs (`make logs ledger`), fix the handler or the data, and the redelivery then applies once. Never add a catch-all to get unstuck.
- Consumers that call a use case pass it `sb_db.uow.joined(uow)`; inside it, `commit()`/`rollback()` are no-ops, so raise to abort. `interface/consumers/account_opened.py` is the example.
- Activities that call a writing use case pass a deterministic idempotency key (the workflow id), because Temporal retries re-run them.
- The workflow has no schedule; its tests start it. Add a per-tenant schedule only when a real job needs one.
- Run the API as `python -m ledger.main` (uvicorn with `log_config=None`), never the bare `uvicorn` CLI, so uvicorn logs go through redaction. Never enable SQLAlchemy `echo`.
- Tests import the in-memory fakes as `from ledger_fakes import ...` (`tests/ledger_fakes.py`). `tests/conftest.py` puts `tests/` on `sys.path` (not a root `pythonpath` entry), so each service owns its own setup. The module is named `<service>_fakes` (never plain `fakes`) because one pytest session shares `sys.modules` across services. The fakes stage writes until `commit()` and mirror `SqlAlchemyUnitOfWork`'s single-use lifecycle; use `fake_joined(outer)` where production passes `sb_db.uow.joined(uow)`.
- DB tests run on their own `ledger_test` database in the shared test Postgres (other members create platform tables in the default one). Request `ledger_db` (sb_app URL), `ledger_sessions` (the one session engine) or `ledger_migrator_url`; never `postgres_url`, `postgres_app_url` or `postgres_migrator_url` directly.
- `tests/integration/db/test_migrations.py` downgrades the shared `ledger_test` schema to base and back (destroying rows), so DB tests are order-dependent and not safe under pytest-xdist. Every test creates its own tenant; never rely on rows from another test.
- Account ids are always server-generated (`OpenAccount`'s `new_id`), never taken from a client: the primary key is global, so a duplicate-id `Conflict` would reveal that an id exists in another tenant.
- The HTTP API contract is committed as `contracts/openapi/ledger.json`. Route function names are its operationIds. After changing a route or schema run `make openapi` and commit the diff; `make openapi-check` fails on drift. Bumping the package version drifts it too (`info.version` comes from the `ledger` distribution version), so re-run `make openapi` after a version bump.
